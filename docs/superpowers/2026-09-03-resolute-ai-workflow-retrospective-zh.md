# 用 AI 做 resolute 移植：方法、机制与取证

这篇写的是**怎么做**，不是**做了什么**。做了什么在同目录的 `2026-08-24-resolute-port-final-state-and-pitfalls-zh.md`（最终状态与坑）、`resolute-modification-catalog-zh.md`（改动分类）和 `specs/`、`plans/` 里，本文不复述技术根因，只在需要时给指针。

写它的原因是：这次移植从头到尾由一个人配合 AI 完成，两个月、190 个构建提交、两个平台从零构建通过、一台在役交换机上线验证，机械重命名与真实修改两个 PR（#7、#8）已于 2026-08-31 合入 `canonical/202605_resolute`。团队接下来还有类似形态的活（别的发行版、别的平台、别的上游分支），所以值得把人机分工的具体形态记下来——哪些环节可以交给 AI 自己跑，哪些环节必须人来卡，以及卡的时候该说什么。

本文的主要证据是 Claude Code 的会话记录，提取和分类的脚本、原始输出、以及**语料本身的严重保留**都在 `data/2026-09-03-prompt-corpus/`。引用的 prompt 一律做过中性化处理——去掉语气词、感叹和情绪性表达，语义不变；转述而非原话的标了「大意」。

## 1. 语料，以及它不干净

先说保留，因为它影响后面每一个数字。

`cleanupPeriodDays` 默认 30 天。2026-08-24 才发现 07-24 之前的会话记录已被自动清扫——那正是迁移主体期——当时把它调到了 3650，但已经晚了。2026-09-03 缺失的会话是**按时间戳从 LLM API 网关的请求日志重建出来的，不是从备份找回的**。

后果可以直接从文件里查证：顶层 75 份 `*.jsonl` 里 **52 份带 `"recovered": true`**，原生文件最早只到 07-25；这 52 份里**没有任何一条记录带非空 `toolUseResult`**，而提取管线第一步正是靠这个字段剔除工具结果，所以那一步对它们是空操作；保真度无法与原件核对，因为原件已经没了。

所以：凡是覆盖 07-02 → 07-24 的计数，都是**重建语料上的估计**，不是精确总数。重跑脚本生成的 `prompts-dedup.tsv` 每行带 `recovered` 列（该文件不入库，含 prompt 原文），任何结论都可以只在 236 条原生输入上复核。

| 项 | 值 |
|---|---|
| 顶层会话记录 | 75 份（52 份重建 / 23 份原生） |
| subagent 记录 | 10 个会话子目录下 56 份 |
| 结构过滤剔除的 sidechain user 记录 | 5,820 条 |
| 人类输入：原始 / 按（时间戳,文本）去重 / 按文本去重 | 1,014 / 969 / **747** |
| 其中来自重建件 / 原生件 | 511 / 236 |
| 携带人类输入的会话 | 68 份 |
| 时间跨度 | 2026-07-02 04:20 → 2026-09-03 06:27，32 个活跃日 |
| 总字符 | 48,140 |
| 均值 / 中位数 / P90 | 64 / 28 / 126 字符 |
| ≤10 / ≤30 / ≤100 字符 | 143 (19%) / 401 (53%) / 647 (86%) |
| ≥300 字符 | 14 条 (1%) |

一半的人类输入在 30 字符以内，86% 在 100 字符以内，全项目人类侧总输入量约 4.8 万字符。这个数字不是效率指标，它说的是这套流程里人的介入形态：绝大多数介入是短的，长输入只有 14 条。

**新项目开工第一件事：把会话记录保留期调长。** 提交历史记录「改了什么」，「为什么这么改」只存在于会话记录里，而它默认 30 天就没了。

## 3. 三种把工作交给 AI 自己跑的机制

SONiC 全量构建动辄几小时，失败点分散在上千个包里，人不可能全程盯着。

### 3.1 `/goal`：交验收条件，不交步骤

做法是给出一个可外部验证的终态，让 AI 自己循环「构建 → 失败 → 定位 → 修 → 提交 → 清理 → 重来」，直到条件满足。判定由 `/goal` 内建的 Stop hook 判定器承担——**这不需要自己配 hook**，本项目 `settings.json` 里一条 hooks 配置都没有。

判定器真正挂上过 9 次。这份表是用记录里 `A session-scoped Stop hook is now active with condition: …` 这条确认消息拉出来的，它是判定器生效的铁证：

| 时间 | 条件 |
|---|---|
| 07-04 15:52 | 在使用 ubuntu 作为 vs target 的 host 成功构建并能正常启动到看 os-release |
| 07-13 07:01 | sonic kvm 启动后显示 ubuntu 26.04 且 7.0 内核；各容器 docker 运行状态也正常 |
| 07-20 06:00 | 写完 plan 后直接按照 plan 派 subagent，构建出 sonic 的 bin 文件为止 |
| 07-20 12:51 | 构建完整的 sonic-broadcom.bin |
| 07-21 15:43 | 成功构建一次 sonic vs 和 sonic broadcom 的 bin |
| 07-23 14:12 | 完成当前 de-fork |
| 07-23 20:02 | vs 和 broadcom 都成功在 \<个人\> 分支上构建 |
| 07-24 15:08 | 完成 plan |
| 07-27 14:10 | 干净构建 vs 和 broadcom 成功，并部署 broadcom 到 dut02 |

条件的写法有一条硬要求：**终态必须是不可伪造的外部事实。** 「kvm 启动后显示 ubuntu 26.04 且 7.0 内核；各容器 docker 运行状态也正常」是三个独立可查的事实；「构建成功」则可以被宽松解释成「主要目标产出了」。

而这张表也说明我们自己没一直守住这条：「完成 plan」和「完成当前 de-fork」恰恰是需要 AI 自述才能判定的条件，不是外部事实。这两次判定的可靠性明显低于前面几次。规矩是对的，执行有漏。

第二条要求关乎判定的依据。判定器的提示词里有这么一句：

```
Based on the conversation transcript above, has the following stopping condition
been satisfied? Answer based on transcript evidence only.
```

`based on transcript evidence only` 是防止「AI 自己宣布自己达标」的屏障。它是内建行为，不需要你写，但需要知道它在——因为下一条坑正来自绕过它。

**中途以文本形式发 `/goal` 可能不挂判定器。** 记录里有 5 次 `/goal` 是在 AI 工作过程中发出的，落盘形式是 `The user sent a new message while you were working: /goal …`。其中 07-20 06:00 和 07-23 14:12 两次同时也注册成了命令，判定器挂上了；另外三次（07-06 17:23 的 os-release 那条、07-13 13:45 的「带邻居 + T0 测试」、07-23 00:41 的「按 clean-rebuild-design 的思路」）**没有任何判定器挂上**，AI 只是把它当普通指令读了一遍。注意别把 07-06 那次和表里 07-04 15:52 那条混起来：后者是一次真实激活，条件也是 os-release，但它是独立的一次。这三次看起来和成功的那几次一模一样，人不会察觉差别。要确认挂上了，就去记录里找那条 `Stop hook is now active` 确认消息。

配套约束同样重要，不然循环会把仓库跑脏：

```
如果遇到问题修改 bug，允许提交但不允许 push。调通为止。
另外 add-host 部分用本地镜像的环境也禁止 commit

同意。但是如果在构建 vs 过程中遇到错误，而且一定需要修改的时候允许修改，
但修改后必须 commit，必须执行完整清理再重新构建
```

「允许提交但不允许 push」是这套机制能放心开的前提：AI 有完整的自主修复权，但产出停在本地，人回来一次性审。「必须 commit + 必须完整清理再重来」保证每轮循环的起点是干净可复现的树，不会出现改了一半靠残留产物跑通的假成功。

关于产出：07-13 那轮内核迁移修掉三个真 bug，但只有一个是循环的功劳。`slave.mk` 残留 `LINUX_KBUILD` 引用（05:54）和 `linux-kernel.dep` 缺 `_CACHE_MODE`（06:20）都在当天 07:01 那次 `/goal` **之前**就修好了；`installer/default_platform.conf` 里 grub.cfg 硬编码旧内核 ABI（07:41）才是循环产物。而这一个恰恰是价值所在——它只有真的 boot 一次才会暴露，而终态被定在「boot 后能读到 os-release」而不是「bin 产出」。

### 3.2 定时看护：把「盯进度」变成一个可重复的诊断清单

长构建会 hang——网络抖动导致容器内 `curl` 卡死，日志停止写入，但 make 进程还活着。人分不清「在跑」和「卡住」，所以用 `CronCreate` 建成定时任务。实际用过两次，表达式分别是 `7,17,27,37,47,57 * * * *`（07-20，broadcom 那轮）和 `3-59/10 * * * *`（07-21，vs + broadcom 两平台），完成后用 `CronDelete` 撤掉。这类任务是**会话级的，会话结束即失效**，不写盘。

07-21 那次的 prompt：

```
每10分钟构建排查（目标：成功构建 sonic-vs 和 sonic-broadcom 的 bin）。
请检查当前构建状态：
1) vs/broadcom 的 make 进程是否存活、日志最后写入时间（判断是否 hang）；
2) 容器内是否有卡住的 curl/网络下载（docker top 看 curl etimes）；
3) 是否已产出 target/sonic-vs.img.gz 或 target/sonic-broadcom.bin；
4) 有无新的 FAIL LOG。
若发现 hang（日志长时间不动 + curl 长时间卡住），按 systematic-debugging 处置
（如 kill 卡住的 curl 让其重试、或预取 deb）。
若构建正常推进则简报一行继续等待。
目标达成（两个 bin 都构建成功）后删除本 cron。
```

四条设计要点：

- **给出判 hang 的具体命令**（`docker top` 看 `curl` 的 `etimes`），而不是让 AI 自己想怎么判断——它会去读日志然后说「看起来在跑」。
- **正常时只准回一行。** 否则每 10 分钟糊一屏状态，人反而看不见异常。
- **明确处置权限**（kill 卡住的 curl、预取 deb），把「发现问题」和「能动手」一起给。
- **达成后自删。** 否则目标完成了 cron 还在跑。

07-20 broadcom 那次更早，也更进一步：把当前进度快照写进了 prompt 本体。

```
④ 若 make 不在且 bin 不存在，看 /tmp/broadcom-m3-bin.log 尾部找失败原因，
  诊断下一类 API 漂移，生成修复 patch，commit，重启构建（后台 nohup + watcher）
当前进度：M1(3 kmod) + M2(3 syncd 容器) + 三个 RFS squashfs 已齐，
正在逐个修 vendor kmod 的 Linux 7.0 API 漂移
（已修 spi/gpio/hrtimer/control/bin_attr/irq/i2c-probe/ioremap/
MODULE_IMPORT_NS/EXTRA_CFLAGS/Maintainer/GPIOF/device_find_child）
```

把状态写进 prompt 而不是依赖上下文，是因为定时任务每次触发都可能落在一个已经被压缩过的上下文里。**任何跨越上下文压缩的任务，状态必须显式携带。**

人工轮询作为兜底一直保留（「怎么样了」这类去重后 9 条不同说法、按出现次数约二十几次）——机制会失效，人的抽查不能停。

### 3.3 subagent 与多 agent 编排

派 `Agent` 工具起 subagent 的选择标准很干净：

```
grub2 和 socat 可以并行。用 subagent 做
起 subagent 试做一下 1.83 吧
subagent 执行吧
```

两种情形派：**互相独立的并行任务**（grub2 与 socat 是两个无关的包），以及**探索性试做**（boost 1.83 先试一把，不确定能不能成）。broadcom 攻坚期（07-20）开过一次 `ultracode` 走 Workflow 多 agent 编排，用在「十几类内核 API 漂移逐个修」这种可以横向铺开的场景。

不适合派 subagent 的是需要连续判断的整合性工作——文档撰写、commit 重组、跨包的一致性审计，这些交给主会话。

## 4. 流程与文档骨架

### 4.1 三段式：spec → plan → 报告

产物物理分开，位置固定：

- `docs/superpowers/specs/<date>-<topic>-design-{zh,en}.md`——设计。方案选型、全局约束、逐文件的切入点表。
- `docs/superpowers/plans/<date>-<topic>-plan-{zh,en}.md`——实施计划。Task 分解、每个 Task 的 Files 清单、`- [ ]` checkbox、退出标准。
- 顶层报告——最终状态、改动分类、代码评审、验证报告。

两个细节让这套骨架真正生效。

**计划文件头部写死技能契约。** 21 份 plan 里 17 份带这一行：

```
> **For agentic workers:** REQUIRED SUB-SKILL: 使用 superpowers:subagent-driven-development
> （推荐）或 superpowers:executing-plans 逐任务实施。步骤用 checkbox（`- [ ]`）跟踪。
```

下一个会话的 AI 打开计划就自动接上正确流程，人不用再交代一遍。缺这一行的 4 份是进度类和收尾类文档，不是遗漏。

**阶段化硬门控。** 迁移设计里定的是五阶段：slave → host OS → 容器 base → vs 容器 → 组装/boot，每阶段有明确退出标准（Phase 0 的退出标准是「`make` 可解析，`BLDENV=resolute` 被选中，尚未拉源」）。这防止 AI 一口气改两百个文件后无法定位失败点。后续几轮（clean rebuild、broadcom、de-fork）都复用了这个形态。

至于「方案选型列 A/B/C 并写明弃选理由」，16 份 spec 里只有约 5 份真做到了。它有用，但别当成既成惯例——它是应该补齐的，不是已经做到的。

### 4.2 长文档逐段生成

2 万行双语文档不是一次生成的：

```
一次只写一段，往下写，直到写完中英文版
一段一段写
继续，一点一点写。一次性不要输出太多
```

逐段生成 + 逐段确认，避免生成一大坨然后发现方向错了。文风也需要显式管：「感觉这版还是有点太 ai 了」「不用加粗标题，小节足矣」「简洁一点，我在公司群发消息」。

### 4.3 双语双文件

每份 spec / plan 出 `*-zh.md` 和 `*-en.md` 两个**独立完整**的文件，英文为 source of truth，对话用中文。不做单文件中英混排。

这条规则纠正过三次才立住：07-03 定下，07-06「双语是中英文各一个文档」，07-10「同意，但中英双语是两个文件」，07-13 又在一份 sonic-mgmt spec 上违反过一次。而且它至今不是全覆盖——`plans/2026-07-24-resolute-ubuntu-source-switch-plan.md` 仍是单文件。所以这是**这次迁移后续文档采用的约定**，不是仓库既有的通则。

### 4.4 AGENTS.md：耐久规则，以及一条错规则的教训

构建仓库根目录的 `AGENTS.md`（174 行）是给 AI 的耐久规则，不是 README。两个设计决定值得复用：

- **明确划界。** 开头写明「项目计划、进度跟踪、设计理由、迁移报告不得在此重复」——只放耐久规则。
- **反教条。** 「不要从本文件推断当前构建环境、包版本或平台支持，去检出分支和相关构建配置里验证。」

但这个文件同时提供了一条反面教训，值得写下来。它的 Git Hygiene 末条至今写着：上游 date 分支可能被 force-rewrite，比对出成千处改动加一个不合常理的旧 merge-base「通常意味着 force-rewrite 而不是本地失误」。这条规则的诊断是**错的**——6.2 第三例已结案：上游从未强推，真因是我们自己就地跑的 `git filter-repo --force`。规则基于错诊断写进去之后就一直生效，没人回头改。同一个文件第 36 行还留着「still WIP on July 13, 2026」这种会过期的状态信息，和它自己「只放耐久规则」的划界相矛盾。

所以：**把踩过的坑写回 AGENTS.md 是对的，但结论被推翻后必须回来订正，否则错规则会一直指导后来的 AI。** 这条 force-rewrite 规则需要一个订正提交。

配套是 `~/.claude/projects/<project>/memory/` 下的 49 条 memory（一事一文件 + `MEMORY.md` 索引）。分工是：AGENTS.md 放**规则**（团队共享、进仓库），memory 放**结论**（个人上下文、含已证伪的假设）。

memory 还当过一次搬运工具：07-02 宿主机从 zfs 根换到 ext4，整个构建环境重建，做法是先让 AI 把不可再生的东西（`rules/config.user`、两处宿主侧修复）写进 memory，换机后照 memory 复原。

## 5. 人的输入落在哪里

747 条去重输入的分类计数。类别互斥、首个命中者胜，未归类的一并报出：

| 类别 | 计数 | 占比 |
|---|---|---|
| 调研 / 核实 / 审计 / 深挖 | 87 | 11% |
| 质疑与推翻 | 53 | 7% |
| push / 提交 / 合入 | 44 | 5% |
| 编排（subagent / goal / cron / jsonl / 并行） | 33 | 4% |
| 授权边界 | 32 | 4% |
| 最小 diff / 回退多余改动 | 25 | 3% |
| 同事 / reviewer / 评审 | 18 | 2% |
| patch 风格（sed / awk / patch 文件） | 17 | 2% |
| 从零重建 / 清理 | 13 | 1% |
| 文档形态与文风 | 13 | 1% |
| 极简推进（继续 / 对 / 同意） | 9 种说法 | — |

两点必须说清，否则这张表会被过度使用。一是**未归类占一半**——那是一次性的实质技术指令，不构成可复用的模式，这是本项目输入的主体。二是极简推进那一行的「9」是**不同说法的数量**（去重后「继续」只算一条）；按出现次数算，推进语加选项字母共 131 次。分类靠关键词正则，量级可信，个别数字不必当精确值引用。

### 5.1 极简推进

```
继续
对
同意
先 C 再 A
B。可以参考之前的 libnl3 / bash 等做法
同意。不过 A 都做完了验证过一遍了再做 C
只需要 track a 和 c，但可以参考 b 的做法
```

这不是省事，是把描述成本外包给了 AI：先用 `superpowers:brainstorming` 让它把方案铺成带编号的选项，然后人只回一个字母。「先 C 再 A」四个字承载了完整的排期决策。前提是选项本身列得足够正交——选项含糊，字母回复就是赌博。

第一条值得单独说：AI 当时的结论是「resolute 自带的 bash 和 socat 编译不过」。这在逻辑上不可能——发行版自己的包当然能在自己的发行版上编译。**推翻它不需要读代码，只需要常识。** 这类失效是 AI 的典型形态：叙述连贯、细节丰富、违反常识。

「别急」这个开头出现 4 次，其中 3 次是在 AI 已经动手时叫停重新调研。

### 5.3 人提假设，AI 做隔离验证

fakeroot 那次值得当成反面教材写。人当时提了一个方向——glibc 改了 syscall 模式导致 fakeroot 解析不了 payload——AI 接着往下查。这个假设**是错的**，真因是宿主 AppArmor 的 `gs` profile 拒绝在构建目录创建文件，而 memory 里的原话是「This was mis-attributed to fakeroot for multiple sessions」：人的假设把 AI 锚在错方向上锚了好几个会话。

所以分工不是「人提假设、AI 顺着查」，而是**人提假设的同时要求 AI 做隔离验证**。那份 memory 记下的做法才是有效的：先不带 fakeroot 单独跑失败的那一步，再读内核审计日志。前者立刻证明 fakeroot 不是必要条件，后者直接指向 AppArmor。

### 5.4 可审阅性是一等目标

工作最终要提到上游，所以「diff 能不能被人读」和「代码对不对」同等重要。这条主线产生了 mech / real 两个分支和已合入的 PR#7 / PR#8：

```
我们要建一大堆 pr 那肯定有一大堆分支，然后我们 stack 起来
202605@orig -> 202605_resolute_pr01 -> 202605_resolute_pr02 -> ...
不 push 不建 pr。我看过再说

经过讨论，我们打算拆成两个 stacked pr。一个是 mechanical changes
（两个 commit，一个是当前的 copy trixie，另一个则是所有的纯 s/trixie/resolute/g；
如果行内有其他修改则丢入另一个真实修改的 pr）；另一个 pr 则是真实修改

感觉可以合成一个 pr；但是原 pr01 里面你要改回那种先复制再修改的模式，否则难以审阅

审计吧，还有明明是一个修改却因为是行级修改散落在多个 pr 的
不是文件级 overlap，而是逻辑级 overlap

然后回头看一下我们将来要提的十个 pr。和同事讨论了一下，
我打算把 broadcom 相关的放到最后
```

核心洞见是**机械变换与真实修改必须分离**：`s/trixie/resolute/g` 这类改动无论多少行，审阅成本都接近零；一旦混进一行真实逻辑修改，整个 diff 就变成不可审阅。所以强制拆成两个 stacked PR——第一个是「原样复制 + 纯重命名」，第二个是「真实修改」。

同理是「先复制再修改」的提交模式：新增 `sonic-slave-resolute/` 时，第一个 commit 原样复制 `sonic-slave-trixie/`，第二个 commit 才改内容。需要说明的是，这个形态是 07-23 重组时为 PR#7 **回填**出来的（mech 分支上先 copy 再 rename 两个 commit），原始工作分支的首个提交本身就带改动。也就是说：可审阅的提交序列可以是评审前重整出来的，不必在开发时就保持。

「逻辑级 overlap」这个概念是审计出来的：同一个语义修改因为落在不同文件的不同行，被机械地拆进了多个 PR，导致每个 PR 单独看都不完整。文件级不重叠不等于逻辑级不重叠。

### 5.5 风格纪律：patch 风格与最小 diff

17 条涉及 patch 风格，25 条涉及 diff 大小，两者是同一个价值观：

```
reviewer 提出了大量的意见。在我们的修改（parent repo 和 submodule）中，
有不少 sed/awk 调用，而不是 sonic 风格的 patch 文件。这不好

上游已有的 sed/awk 等没问题，但我们不能新增
那你再核实下当前的 sed/awk 和 patch，哪些可以进化成直接改？

bash diff 根本不是最小：换行格式、可选的行号修改、尾部的 patch 生成器，
这些都可以保留原来。无非多一些 offset 罢了

你是不是做了很多可选的事情。大量的 mv 修改和 changelog 修改真的是必须的吗
对于 -mv 这种，我们要保证没有任何一处是我们修改的
各种注释加的太长了
```

「无非多一些 offset 罢了」这句体现了**成本权衡方向和 AI 的默认相反**：AI 倾向于让 patch 精确对齐（干净，但 diff 大），对上游 fork 该选容忍 offset 警告（脏一点，但 diff 小）。这个偏好 AI 不会自己产生，必须反复注入——每次它都会漂移回「顺手改好」。

由此固化出的规则（已入 memory 和 AGENTS.md）：**子模块和拉取型源打 `.patch` overlay，在树源码直接改源码，不用 sed/awk 就地改。**

## 6. 事故与结构性风险

技术根因一律见 `2026-08-24-resolute-port-final-state-and-pitfalls-zh.md`，这里只留人机协作层面的教训。

### 6.1 双仓库的 cwd 漂移——两起实际事故

AI 的 shell 工作目录会被静默重置到主工作目录（输出里会出现 `Shell cwd was reset to …`），而两个仓库的相对路径结构相似，命令看起来是对的。两次都造成了实际后果：07-23 会话续传后一次 `make … reset` 落在了文档仓库；08-19 一次 `git commit --amend` 打到文档仓库，把 `0ee46067d8` 的 commit message 覆盖成了别的文案（树没变，`reset --soft` 复原）。同期还有一次目标仓库看错，是同一根因的轻量版本。

**唯一可靠的消除方式是所有 git 写操作显式 `git -C <repo>`**，不依赖 cwd。详见 memory `two-repo-cwd-hazard`。

### 6.2 三次「叙述连贯但证据不足」的因果归因

- **fakeroot「payload not recognized」**被当成 bash 构建崩溃主因，错了好几个会话。见 5.3。
- **show/plugins**。这里其实是**两个不同故障**，我们一度用一个「真因」把它们吞了：`show ip …` 报 "No such command" 是 db 未就绪或缺 minigraph；`show.plugins.*` 的连字符导入告警是上游 bug（`import_module` 不接受连字符）。而真正的**导入失败**是 `dhcp-relay.py:83` 模块级 `ConfigDBConnector()` 撞上 db 未就绪，「连字符导致导入失败」这个说法被三路证伪（合成模块 / wheel / 实际 rootfs 布局）。教训是：症状相似的多个故障要先分开对号，再谈根因。
- **「上游 force-rewrite 了 202605」**。真因是我们自己就地跑的 `git filter-repo --force`。决定性证据是 GitHub Activity API（194 次 pr_merge、`force_push=0`）、本地 `.git/logs/HEAD`，以及「分叉点恰好是首个签名 commit 的父节点」这个论证；gharchive 的 BigQuery 查询只覆盖 194 次推进中的 35 行（18%），是被证明不可靠的辅助源，不能拿它下结论。完整过程见 `2026-08-31-sonic-202605-workflow-forensics-zh.md`。

共同教训：**AI 给出的因果链条越流畅、细节越丰富，越需要一个不依赖它叙述的独立证据源。** 而且推翻之后要回头改 AGENTS.md（见 4.4）。

### 6.3 缓存掩盖真 bug

完全从零重建（修复都在 07-21）暴露过三个被缓存层掩盖的真 bug，技术细节见 pitfalls 4.3；这里只留两条协作层面的结论。

一是**验收标准必须是完全从零重建，不能是「增量构建过了」**。本项目最终跑了两轮（08-23、08-27，vs + broadcom 双平台），两轮是当时的判断，不是什么普适数字。清零顺序有讲究：`fsroot*` 是 root 属主，必须先 `sudo rm` 再 `git clean`。

二是**「重试后过了」有可能是假的**：`.flags` 是独立的 make 目标，当一个包已有旧产物时（增量或平台切换构建），失败包重试会被判 up-to-date 而静默复用旧产物。

顺带一句关于引用的纪律：这三个 bug 里 `build_image.sh:51` 那个，现在那一行已经是修好的样子（`sudo -E env …`），dash-engine 那笔也已被上游 #28587 取代。**写复盘时引用行号，要标明是「当时」**，否则读者照行号去看会得出相反结论。

### 6.4 虚假的「已上游」注释——是外部 reviewer 抓出来的

AI 会把「跳过了」写成「已上游修复」的注释。PR#8 的四条指控经核实全部属实——lldpd 和 flashrom 的相关注释不成立，处置是两者都退回源构建。

值得强调的是：**这批假注释不是我们自己的流程抓出来的，是外部 reviewer 抓出来的。** 人机闭环里没有任何一环去挑战 AI 写下的「已上游」断言。所以对策是把它变成一道显式工序——**周期性的声明审计**：凡是注释里出现「已上游」「不再需要」「等价于」这类断言，都要单独核一遍。记录在 memory `resolute-defork-upstreamed-claims-audit`。

### 6.5 子模块不跟着超仓 rebase

只 rebase 超仓、子模块分支不动，会导致 gitlink 保留旧提交、上游修复被静默丢弃（SAI 计数器恒零就是这么来的）。技术细节见 pitfalls 4.1。

协作层面的对策是把规则变成脚本：`scripts/submodule-ff-audit.sh`（在构建仓库里），每次同步上游后跑一次。**能脚本化的规则不要留在人的注意力里。**

## 7. 给下一次同类工作的清单

按开工顺序排列。标了「特例」的是本项目的具体取值，不是通则。

开工前：

1. 把 `~/.claude/settings.json` 里的 `cleanupPeriodDays` 调长。它是「为什么」的唯一载体，默认 30 天会清掉——而清掉之后从网关日志重建的语料是有损的（见 §1）。
2. 对齐前提：模型与档位、需要的插件与技能、可用的内建工具名（`/goal`、`CronCreate`、`Agent`）。方法依赖这些，换环境要先确认它们存在（§2）。
3. 在目标仓库根目录写 `AGENTS.md`，只放耐久规则，写明「计划和进度不在此重复」以及「不要从本文件推断当前状态，去分支里验证」。同时**建立订正机制**：结论被推翻后回来改，否则错规则会一直生效。
4. 定好文档三段式的位置和命名。双语双文件是团队约定（特例），按你们的实际需要定。
5. 如果并行操作两个以上仓库，从第一条命令起就强制 `git -C`。

进行中：

6. 每个阶段先出 spec 再出 plan（Task 分解、Files 清单、checkbox、退出标准）。plan 头部写死 `REQUIRED SUB-SKILL`。spec 里列方案 A/B/C 与弃选理由是应该做到的，本项目只做到约三分之一。
7. 长任务用 `/goal` 交条件不交步骤。条件必须是不可伪造的外部事实（本项目有两次没守住）。**确认判定器真的挂上了**——去记录里找 `Stop hook is now active` 那条确认消息；工作中途以文本发的 `/goal` 有可能不挂。配「允许 commit、禁止 push」。
8. 长构建用 `CronCreate` 配定时看护：给判 hang 的具体命令、明确处置权限、正常时只回一行、把进度快照写进 prompt 本体、达成后 `CronDelete`。注意会话级 cron 随会话结束失效。
9. 派 subagent 只用于独立并行任务和探索性试做；整合性工作留在主会话。
10. 长文档逐段生成逐段确认。文风要显式管。
11. 授权用「允许 X，禁止 Y」；例外用「仅此一次，我显式同意」（会被复用，每次单独说）；不可逆动作推到验证之后。
12. AI 的结论违反领域常识时直接否决，并给出那个具体反例——不要说「再查查」。人提假设时，同时要求 AI 做隔离验证，别让假设变成锚。
13. 反复注入「最小 diff」和「可审阅性」这两个价值判断，它们不会自己维持。机械变换与真实修改分离；可审阅的提交序列可以在评审前重整出来。

收尾前：

14. 完全从零重建，双平台。不接受「增量构建过了」。轮数按你们的风险偏好定（本项目两轮，特例）。
15. 审计所有「已上游 / 不再需要 / 等价于」类注释。本项目这一步是外部 reviewer 补上的，说明它必须是显式工序。
16. 跑子模块 ff 审计脚本（本项目是 `scripts/submodule-ff-audit.sh`，特例；通则是「能脚本化的规则就脚本化」）。
17. 把已证伪的假设写进 memory——反向结论能防住重复劳动。
18. 引用行号和文件状态时标明「当时」，因为后续提交会让它们失真。
19. 发布前人工过一遍隐私：内网 IP、IPv6 前缀、用户名、凭据。AI 不会自己意识到内网拓扑是敏感信息。

## 附录 A：提取管线

脚本、原始输出和完整的口径说明都在 `data/2026-09-03-prompt-corpus/`（`mine-prompts.py`、`corpus-stats.txt`、`README.md`；`prompts-dedup.tsv` 含 prompt 原文，不入库，本地重跑生成）。运行 `./mine-prompts.py` 可重新生成全部数字。

三个步骤，每步都是先做错了才发现的。

**一、结构过滤。** 保留 `type=="user"` 且 `isSidechain` 非真、`isMeta` 非真、`toolUseResult` 为空的记录。subagent 的对话也以 user 角色落盘（顶层 5,820 条），工具结果同样，harness 注入的 skill 正文和 agent 列表也是——后者靠 `isMeta` 捕获。**漏掉 `isMeta` 会让一份 240 KB 的 skill 手册被算成一条人类输入**，长度统计直接报废。

**二、文本过滤，但要区分「丢弃」和「剥壳」。** 大部分以 user 角色注入的非人类文本应当丢弃（`<system-reminder>`、hook 反馈、任务通知、`/goal` 判定器提示词、转发的 agent 消息等）。但有四种形态是**包裹**真实输入而非取代它，丢弃会连人说的话一起丢掉：

- `The user sent a new message while you were working:\n<真实输入>`
- `<ide_selection>` / `<ide_opened_file>` 块
- `The user selected the lines N to M from <path>` 前缀
- 尾部追加的 `CRITICAL: Respond with TEXT ONLY …` hook 后缀

斜杠命令要保留，方式是取 `<command-args>`（那是人写的文本），丢掉 `<command-name>` 外壳。

**三、两个去重口径，因为哪一个单独用都不对。** 恢复会话时新会话文件会把旧消息重新落盘。按（时间戳,文本）去重得 969，会把重放算进来；按文本去重得 747，会把真实的重复输入（「继续」）压成一条。**统计「不同指令的数量」用文本口径，统计「推进语频次」用时间戳口径。**
