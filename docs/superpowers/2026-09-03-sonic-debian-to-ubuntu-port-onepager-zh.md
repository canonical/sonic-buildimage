# 我们如何把 SONiC 从 Debian 搬到 Ubuntu

SONiC 是越来越多数据中心交换机背后的开源网络操作系统，它的社区构建一直基于 Debian。我们认为它应该像旁边的服务器一样跑在 Ubuntu 上：一套受安全维护的基础系统、长期的支持周期、从宿主机到交换机同一套内核与工具链。于是我们把社区构建搬到了 Ubuntu 26.04 LTS，覆盖虚拟交换机和 Broadcom 交换机。

## 改动概览

我们原以为只要换个基础镜像；结果发现了五类差异：

- **发行版结构。** GRUB 和内核的打包方式不同，`resolvconf` 不再存在，rsyslog 和 hostname 带着 enforce 模式的 AppArmor profile。
- **工具链更新。** GCC 15 默认 C23；Python 3.14 强制 PEP 668。更新不总是更好——我们把 Boost *退回*到 Debian 用的版本。
- **Linux 7.0 内核。** Broadcom 树外驱动里十几类 API 漂移。
- **写死的发行版代号。** 「trixie」烤进了容器模板和构建规则。
- **更严格的打包工具。** dpkg 拒绝不规范的元数据；调试包变成了意料之外的 `.ddeb` 文件。

两条规则贯穿所有决定：Ubuntu 不需要的一律不动，机械改名和真实改动分开，让审阅者能一眼区分。两个镜像都能从干净的检出构建出来；Broadcom 镜像已在一台 Dell 交换机上验证，BGP 正常建立。

## 我们的 AI 天使（agents）

一位工程师加 Claude Code，两个月做完。

**我们的方法。** 我们交给 agent 的是一个终态，不是任务清单：「虚拟机在 7.0 内核上启动 Ubuntu 26.04，所有容器都在运行。」它自己循环——构建、失败、诊断、修复、清理、重试。允许 commit，不许 push。这个循环找到了一个任何构建日志都显示不出来的 bug：installer 里一条只在启动时才出问题的路径。

**人工审阅。** agent 的每个结论都是待验证的断言，最锋利的纠正来自常识——Ubuntu 自己的 bash 不可能在 Ubuntu 上编不过。相互独立的 AI 审阅者不是保证：三个审阅者收敛到了同一个错误答案。一位外部的人类审阅者抓到了未经核实就写下的「已在上游修复」注释。

**测试。** 验收意味着清空构建缓存从零重建——带缓存的构建曾掩盖过真正的 bug。干净的退出码什么都保证不了：FRR 构建正常，却没有打进 SONiC 的转发模块，直到真机上 BGP 起不来才发现。重新打开包测试之后又浮出了最具 Ubuntu 特色的 bug：一个默认链接选项让测试用的 mock 拦截不到库调用。一个构建标志修好了它，测试套件在没有 Redis 的情况下通过。
