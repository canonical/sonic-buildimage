# Is sw1 an ONIE install, and how would we migrate it to resolute

**Date**: 2026-09-09
**Subject**: `sw1` (`<SW1-MGMT-IP>`, Dell EMC S5232F-ON / TD3, platform `x86_64-dellemc_s5232f_c3538-r0`, a lab fabric node, AS 65302)
**Nature of this document**: **read-only reconnaissance plus a plan**. Nothing was written to sw1 — disk, configuration and NVRAM were all left untouched.
**Prerequisite reading**: [ONIE multi-boot mechanics and an installation SOP](2026-09-09-onie-multiboot-and-ubuntu-sonic-install-sop-en.md) (the four-layer boot model, `sonic-installer` traps, the parallel transfer technique)

---

## Summary

| Question | Answer |
|---|---|
| Is sw1 an ONIE install? | **Yes** — and a textbook one |
| Same situation as dut02? | **No, and considerably simpler.** dut02 was *not* originally ONIE-installed (cloud-init + PPA bare `.deb`), which is why it needed the shrink + dual-boot dance. sw1 does not |
| Is migration feasible? | Yes. Platform support, disk space, the DB migration chain and the ONIE fallback have each been verified |
| Recommended path | `sonic-installer install` into the **second image slot** — not an ONIE reinstall |
| Can we start now? | **No.** Three blockers must be cleared first: the dangling `resolv.conf`, the absent console recovery path, and ownership sign-off |

## 1 · Assessment: sw1 is a standard ONIE install

Seven pieces of evidence, all from this read-only pass:

| Criterion | Measured on sw1 | Meaning |
|---|---|---|
| `/host/machine.conf` | Complete `onie_*` variable set: `onie_boot_reason=install`, `onie_version=3.40.1.1-9`, `onie_platform=x86_64-dellemc_s5232f_c3538-r0`, `onie_exec_url=http://<IMG-SRC>:8080/sonic-broadcom.bin` | **Decisive** — this file is generated by the ONIE installer |
| Partition layout | `sda1` EFI 256M / `sda2` **ONIE-BOOT** 128M / `sda3` SONiC-OS 32G; **27.3 GiB unallocated** at the tail | Canonical ONIE layout, and no third-party NOS partition |
| EFI entries | `Boot0005* SONiC-OS` (BootCurrent) / `Boot0004* ONIE` / `Boot0000* EDA-DIAG` | The ONIE entry is intact |
| `/host/grub/grub.cfg` | Full `saved_entry`/`next_entry`/`onie_entry` block plus three menuentries: `SONiC-OS-feat_dhcp-rock.0-b2f3ebaf9`, `EDA-DIAG`, `ONIE` | Layer 2 is healthy; the one-shot jump into ONIE works |
| `/EFI/debian/grub.cfg` | `search --no-floppy --label --set=root SONiC-OS` | Single NOS — **none of dut02's entry-point contention** |
| Image slots | Exactly one: `/host/image-feat_dhcp-rock.0-b2f3ebaf9` (618 MB) | The second slot is free |
| EDA-DIAG | Separate eMMC `mmcblk0p2` (3.5G, PARTUUID differs from sda) | Usable as staging, and unaffected by anything done to sda |

**The key difference from dut02**: dut02 required a shrink and dual-boot because that machine was **not** ONIE-installed — somebody had laid down a bare-`.deb` Ubuntu via cloud-init and a PPA, one root partition filled the entire disk, and cloud-init's `growpart` re-expanded it on every boot. sw1 has none of that: the disk was partitioned by ONIE in the first place, `/host` already reserves room for two images, and there is 27.3 GiB free at the tail. **Stage 2 of the SOP — shrink and dual-boot — simply does not apply to sw1.**

## 2 · Feasibility assessment

### 2.1 Verified green lights

- **Platform is supported** — unpacking the payload of our own `.bin` offline confirms `x86_64-dellemc_s5232f_c3538-r0` is present in `installer/platforms_asic`, and `device/dell/x86_64-dellemc_s5232f_c3538-r0` is in the resolute tree (retained after the broadcom build was trimmed to dell/XGS).
- **The same hardware is already proven** — dut02 is also an S5232F/TD3, and our self-built resolute broadcom image ran there end to end (CANCUN CIH–CFH `LOADED 06.15.00`, create_switch OK, front-panel ports up). sw1 is the same model with the same HwSKU (`DellEMC-S5232f-C32`).
- **Ample space** — 27 G free of `/host`'s 32 G; the image is 2.03 GiB. The second slot is empty, so **nothing gets evicted**.
- **The DB migration chain is complete** — sw1's schema is `version_202405_01`; our resolute is 202605. Every hop exists in `db_migrator.py`, and `CURRENT_VERSION = 'version_202605_01'`:

  ```
  202405_01 → 202405_02 → 202411_01 → 202411_02 → 202505_01 → 202511_01 → 202605_01
  ```

  Reading what each hop actually does, **almost all of them are no-ops for this box**: the `check_has_sonic_dhcpv4_relay_flag()` branch repeated at every hop does not apply; `migrate_ipinip_tunnel()` (202405_02) — this box has no IPinIP tunnels; `migrate_ipinip_tunnel_ecn_mode_mellanox()` (202511_01) is **mellanox-only** and broadcom skips it. The only hop that actually changes anything is `migrate_flex_counter_delay_status_removal()` (202505_01). **Config migration risk is low.**
- **The ONIE fallback is present** — ONIE 3.40.1.1-9, the same version as dut02, so the rescue technique (dropbear + udhcpc picking up the same mgmt IP, root with an empty password) carries over directly; the SOP's layer-1 section has the full inventory.
- **Secure Boot is not in play** — `mokutil --sb-state` returns "This system doesn't support Secure Boot".

### 2.2 Blockers (must be cleared before starting)

**① A dangling `/etc/resolv.conf` will make `sonic-installer install` fail**

Measured:

```
/etc/resolv.conf -> /run/resolvconf/resolv.conf     (target does not exist)
getent hosts archive.ubuntu.com  → rc=2             (DNS entirely broken)
```

`sonic-installer install` copies `/etc/resolv.conf` into the new image's chroot during `migrate_sonic_packages`, and **a dangling link fails there** — we hit exactly this on dut02.

This is not a one-off fault on sw1 but a **structural regression of the Ubuntu port**: the Ubuntu archive has no real `resolvconf` package (`systemd-resolved` claims the name via `Provides/Replaces/Conflicts`), while the SONiC image still creates that symlink. Our resolute build fixes it; the `feat_dhcp-rock` build sw1 runs does not. **So it must be worked around by hand before installing, and the new image resolves it afterwards.**

**② There is no console recovery path**

dut02 had a console server (`<CONSOLE-SERVER>:7011`, two-stage login). **No port mapping is known for sw1** — the console server address itself answers pings, but which port reaches sw1 is unknown.

This is not a formality: installing remotely over a 360 ms link means that if the new image fails to boot, or boots without bringing up management, **there is no recovery without someone physically present**. ONIE rescue is half a safety net (it DHCPs onto the same mgmt IP, as proven on dut02) but only if you can still reach ONIE. **Establish console access first.**

**③ Ownership is not confirmed**

This is somebody else's **active** lab device: on 9/4 someone ran `config save` and rebooted (current uptime is 5 days and the config_db mtime `2026-09-04 10:01:45` matches), and on 9/8 an admin logged in from another subnet. Migration replaces the entire OS, so **explicit owner sign-off is required**.

### 2.3 Risks (not blocking, but they belong in the acceptance baseline)

- **Existing configuration defects will carry over verbatim.** sw1's `config_db.json` holds several empirically confirmed defects: Po205 absorbs eight ports into one LAG (the plan calls for two ports to each of four leaves), the v6 addresses on Po204–208 are missing a hex digit (`ac1:` should be `ac11:`), and the j18/j19 neighbor lines are themselves wrong. **Migration is not the moment to fix these** — change one variable at a time. But this yields a hard constraint: **the acceptance baseline must be the values measured before migration, never the planned values**, or long-standing config defects will be misread as migration regressions.
- **The pre-migration baseline is itself incomplete** (which lowers the risk): v4 has 11 peers with **4 Established**, v6 has 6 peers, there are **73** ASIC routes and 12 containers. There is no northbound path — both uplink peers (`agg-sw1` / `agg-sw2`) sit in `Active`, uplink optical power is symmetrically broken (one port lit and one dark in each uplink LAG), and A/B testing already ruled out FEC and placed the fault on the far end. **This box is not currently carrying north-south traffic.**
- **`config_db.json.save` is not a rollback point** — it is an 18 257-byte factory sample (`hostname: sonic` / `bgp_asn: 65100`). The real config is `/etc/sonic/config_db.json`, 46 610 bytes, mtime `2026-09-04 10:01:45`.
- **The two-image ceiling** — after this migration both slots are full. Installing a third image later **silently evicts** the oldest non-current one (mechanism in the SOP, layer 3).
- **⚠️ There is no usable source to reinstall the original image.** The machine holds **no `.bin` anywhere**; the `onie_exec_url` recorded in `machine.conf` points at `http://<IMG-SRC>:8080/sonic-broadcom.bin`, and while that host answers pings, **port 8080 does not respond within 10 s**; its sibling sw2 currently refuses SSH and cannot serve as a backup source. **This means the last-resort "reinstall the original via ONIE" path is currently broken** — mitigation in §4 stage 0.

## 3 · Recommended approach: coexisting second image

**Use `sonic-installer install`, not `onie-nos-install`.**

| | `sonic-installer install` (recommended) | `onie-nos-install` |
|---|---|---|
| Existing image | Preserved as a one-command rollback | **Rebuilds the SONiC-OS partition, wipes it** |
| Configuration | Auto-copied to `/host/old_config`, migrated on first boot | Lost |
| EFI entries | Untouched | Modified (on dut02 it removed another NOS's entry) |
| Rollback | `set-default` + reboot, one command | Needs the original `.bin` — **which we do not have** |
| Viable today | Second slot free, nothing evicted | Possible but irreversible |

Given that the original image's reinstall source is dead (§2.3), **keeping the existing image slot is the only rollback guarantee we have**, and that alone rules out the ONIE reinstall route.

## 4 · Procedure

### Stage 0 · Prerequisites (do not start without these)

1. **Establish console access** — obtain sw1's console server port and **log in once to prove it works**. This is the only way to see the grub menu if the new image fails to boot.
2. **Obtain owner sign-off** — agree the migration window and how many reboots are acceptable.
3. **Back up the existing image directory** (mitigating the dead reinstall source in §2.3) — it is only 618 MB, so keep a copy locally and on EDA-DIAG:
   ```bash
   sudo mount /dev/mmcblk0p2 /mnt/eda && sudo mkdir -p /mnt/eda/backup
   sudo tar czf /mnt/eda/backup/image-feat_dhcp-rock.tar.gz -C /host image-feat_dhcp-rock.0-b2f3ebaf9
   sudo cp /host/grub/grub.cfg /mnt/eda/backup/grub.cfg.pre-migration
   ```
   This is not a bootable `.bin`, but it is enough to restore in place if the grub entry or the image directory is damaged.
4. **Capture the baseline** (needed for acceptance — and this machine changes, so re-capture if the work spans days):
   ```bash
   sudo cp /etc/sonic/config_db.json ~/config_db.json.pre-migration
   stat -c "%y %s" /etc/sonic/config_db.json          # expect 2026-09-04 10:01:45 / 46610
   sudo sonic-installer list; redis-cli -n 4 hget "VERSIONS|DATABASE" VERSION
   docker ps -q | wc -l                                # baseline 12
   vtysh -c "show bgp ipv4 summary" > ~/base-bgp4.txt  # baseline v4 11 peers / 4 Established
   vtysh -c "show bgp ipv6 summary" > ~/base-bgp6.txt  # baseline v6 6 peers
   redis-cli -n 1 --scan --pattern "ASIC_STATE:SAI_OBJECT_TYPE_ROUTE_ENTRY:*" | wc -l   # baseline 73
   show interfaces status > ~/base-intf.txt
   ```

### Stage 1 · Fix `/etc/resolv.conf` (blocker ①)

```bash
sudo rm -f /etc/resolv.conf                       # delete the dangling symlink first; do not just redirect onto it
printf 'nameserver <DNS-1>\nnameserver <DNS-2>\n' | sudo tee /etc/resolv.conf
getent hosts <any resolvable name> && echo OK
```

Record this in the rollback list — it is a temporary change we introduced. After the new image is installed, resolute's `resolv-config.service` takes over and the file should be "a regular file with a SONiC header".

### Stage 2 · Transfer the image (2.03 GiB over a 360 ms link)

A single scp stream collapses on this path. Use the SOP's stage-4 technique — four parallel streams with size-based resume, aggregating ~3.8 MB/s:

```bash
split -d -b 548M /home/sheldon-qi/sonic-buildimage-resolute/target/sonic-broadcom.bin ~/rparts/rpart-
# four parallel scp streams into /host/staging/, each with retries; then cat + sha1 on the far end
```

Land it in `/host/staging/` (27 G free, more than enough). Re-check the sha1 immediately before installing, and let the installer's built-in `payload_sha1` self-check run.

### Stage 3 · Install the second image

```bash
sudo sonic-installer list                 # confirm there is still only 1 image (nothing will be evicted)
df -h /host
yes | sudo sonic-installer install /host/staging/sonic-broadcom.bin
sudo sonic-installer list                 # expect both images present, Next = resolute
```

**Do not reboot immediately** — first confirm `Next` points where you intend and that `/host/old_config` holds a copy of the configuration.

### Stage 4 · Switch over

```bash
sudo reboot
```

**Watch the console** established in stage 0. First boot runs all six `db_migrator` hops and is slower than usual; SONiC's monit convergence normally takes well over ten minutes, so do not declare failure within the first 15.

### Stage 5 · Acceptance

```bash
sudo sonic-installer list | grep Current                       # = the resolute version string
uname -r                                                        # expect 7.0.0-1002-sonic
grep VERSION= /etc/os-release                                   # expect Ubuntu 26.04 Resolute
redis-cli -n 4 hget "VERSIONS|DATABASE" VERSION                 # expect version_202605_01 (proves all six hops ran)
docker ps -q | wc -l                                            # >= 12
redis-cli -n 1 --scan --pattern "ASIC_STATE:SAI_OBJECT_TYPE_ROUTE_ENTRY:*" | wc -l   # >= 73
vtysh -c "show bgp ipv4 summary" | tail -3                      # Established >= 4
bcmcmd "cancun stat"                                            # CIH/CMH/CCH/CEH/CFH LOADED 06.15.00
ls -l /etc/resolv.conf; systemctl is-active resolv-config       # regular file + active
show system-health detail | grep -A2 Services                   # use this; do not count grep -c OK
```

**Compare against the baseline, not against the plan.** The northbound path was already down and Po205 was already an eight-member LAG — those staying that way after migration is the correct result.

## 5 · Rollback matrix

| Failure level | Action | Requires |
|---|---|---|
| New image boots but behaves wrongly | `sudo sonic-installer set-default SONiC-OS-feat_dhcp-rock.0-b2f3ebaf9` + reboot | SSH reachable |
| New image will not boot / no management | console → pick the old image in the grub menu | **console (stage 0)** |
| Cannot even reach grub | UEFI `Boot0004` → ONIE rescue → mount `sda3`, fix grubenv / restore grub.cfg | ONIE rescue can DHCP onto the mgmt IP |
| Image directory or grub entry damaged | restore `image-feat_dhcp-rock.tar.gz` + `grub.cfg.pre-migration` from EDA-DIAG | stage 0 step 3 |
| Configuration needs reverting | `sudo cp ~/config_db.json.pre-migration /etc/sonic/config_db.json && sudo config reload -y` | stage 0 step 4 |
| Nothing else works | ONIE reinstall of the original image | **no source available — see §2.3; this path is broken** |

## 6 · Open items (resolve each before starting)

1. **The console server port mapping for sw1** — blocking; must be proven by an actual login.
2. **Owner sign-off and the migration window** — blocking.
3. **A source for the original `.bin`** — `<IMG-SRC>:8080` no longer responds and sw2 is currently unreachable. Either locate the owner's original `.bin`, or accept and record in the change ticket that the rollback ceiling is image-directory restoration with no ONIE reinstall path.
4. **Whether to fix the config defects at the same time** — recommendation: **do not** do it in the same window. First prove that the same configuration behaves identically on the new image, then open a separate window for Po205 and the v6 typos.
